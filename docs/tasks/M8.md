# M8 · 打包平面直通：ring 改打包排列、RGBA 按需、`eTF_R8` 上傳、`acceptLayouts` 協商、色度位置

對應：`docs/design/M6-ui-source.md` §3（`layout`、`planeY/U/V/A`、`colorMatrix`、`colorRange`、`chromaSiting`、`flags` bit3、規則 5～8）、§5.1、§5.2、§10（`eTF_R8` 可用、同名重建同 id、RAM 增量待查、色度位置的結論）、§11。前置：M6a／M6b／M7 已併入。模型：Opus。工作樹 `E:/coding crycry/cev-wt-m8`，分支 `m8`。引擎樹 `E:/coding crycry/CRYENGINE_Source_CEVPlayer_XTFrame`。**不合併、不推送。** 消費端（CryXTUI）尚不能取樣平面排列——由自測扮演消費端並以 CPU 參考轉換驗證像素。

動手前以程式核對下列前提；不符就停下回報。先寫會失敗的測試。

## 要做的事

1. **ring slot 一律是打包排列**（`Core/src/FrameRing.cpp`、`VideoDecoder.cpp` 的 `WriteFrame`）：4:2:0 且寬為偶數時，每格一塊連續緩衝、列寬＝影片寬 `w`（緊密，不對齊）：Y `(0,0,w,h)`；U `(0,h,cw,ch)`、V `(cw,h,cw,ch)`；alpha `(0,h+ch,w,h)`（有 alpha 時）。其他取樣格式（4:2:2、4:4:4、4:4:0）與奇數寬維持現行的分離平面配置，且只能輸出 RGBA8。`FrameView` 增加打包緩衝的指標、總尺寸與四個矩形。
2. **RGBA 按需**：RGBA 緩衝的配置與 `ConvertSlot` 只在「需要 RGBA8」時進行；需要與否可在播放中切換（Core 新 API，例如 `SetOutputRgba(bool)`；切換在幀邊界生效：開→之後 commit 的幀帶 RGBA；關→釋放 RGBA 緩衝。配置不得發生在穩定播放的每幀路徑上）。切換不重新載入、不動時鐘與聲音。
3. **排列的決定**（模組）：surface 播放器的排列＝打包平面，若且唯若 (a) 串流是 4:2:0 偶數寬、(b) 聚合的 `acceptLayouts` 含對應排列（無 alpha → `CTS_LAYOUT_PACKED_YUV420`；有 alpha → `CTS_LAYOUT_PACKED_YUVA420`）——聚合規則照 §3 規則 5：所有活著的消費端都接受才算；沒有消費端或有匿名（`consumer`＝0）消費端 → RGBA8、(c) 播放器沒有同時輸出到全螢幕或材質、(d) cvar `cev_allowPlanar`（預設 1）為真。否則 RGBA8。條件改變時在下一個 tick 切換：釋放舊貼圖、建立新貼圖（RGBA8：`eTF_R8G8B8A8` w×h；打包：`eTF_R8`、`w × (h + ch [+ h])`、`FT_NOMIPS`）、`generation`＋1、`contentSerial`＋1，並立即上傳目前這一幀（切換不得出現一幀空貼圖：新貼圖建立的同一個 tick 內要有內容；若當下沒有可用的幀資料，保留舊貼圖到有為止）。為避免來回切換：排列改變後至少維持 30 次 tick 才允許再切。
4. **上傳**：打包排列時以 `UpdateTextureInVideoMemory(id, packed, 0, 0, w, packedHeight, eTF_R8)` 上傳整塊（緊密列）。
5. **快照**（`Module/Contract/TexSource.cpp`）：`layout`、四個平面矩形（貼圖內的 texel）、`colorMatrix`（601／709，沿用 Core 既有的判定）、`colorRange`、`chromaSiting`、`flags` bit3＝0（VP9 alpha 的色彩平面未乘 alpha）、bit0（premultiplied）在打包排列時為 0。`width`／`height` 仍是畫面尺寸。`IVideoPlayer::GetPixelLayout()` 回報實際排列；描述表的 `PixelLayout` 查詢、FlowGraph `VideoUI:SurfaceInfo`、`cev_surfaces`、`cev_stats` 同步。
6. **色度位置**：Core 的 demuxer 讀 Matroska 的 `ChromaSitingHorz`／`ChromaSitingVert`（libwebm 已解析），對應到 `CTS_SITING_LEFT`／`CENTER`／`TOPLEFT`；沒標時回報 LEFT。現行 CPU 轉換（最近點）不改。匯入轉碼（`FfmpegCommands.cpp`）不強制指定色度位置，沿用來源。
7. **RAM 用量調查**（§10：1080p 行程 RAM 增量 110～160 MB，ring 推算只有 44～51 MB）：在動手改 ring 之前先量清楚增量由誰構成（ring、libvpx 內部參考幀與執行緒緩衝、解封裝緩衝、引擎貼圖的 CPU 端複本、音訊），方法與數字進報告；改完後再量一次（打包＋不配 RGBA）。
8. **參考取樣器**（測試與文件用，不進執行期路徑）：在 Core 的測試工具放一個 CPU 函式，照契約的語意把打包緩衝轉成預乘 RGBA8（給定矩形、矩陣、範圍、位置；色度以雙線性內插並把取樣座標夾在各平面矩形內半個 texel），作為消費端著色的參考實作；另提供與現行最近點轉換相同取樣方式的變體以便逐像素比對。把這段的數學（YUV→RGB 的係數、limited／full 的偏移與縮放、夾取規則、alpha 的預乘順序）寫進 `docs/design/M6-ui-source.md` 新的一節「平面取樣的參考實作」，供消費端照做。

## 測試

- Core 自測：打包排列的配置與矩形（含奇數高、有無 alpha）；`WriteFrame` 後各平面內容與解碼器輸出逐位元組相同；非 4:2:0／奇數寬退回分離平面；RGBA 開關在播放中切換（幀邊界、無配置於穩定路徑——以既有的 `allocs` 計數驗證）；色度位置的讀取（有標、沒標）；參考取樣器（最近點變體）對打包緩衝的輸出與現行 `ConvertSlot` 的 RGBA **逐位元組相同**（六支量測素材各取數幀）。
- `cev_contract_selftest`：沒有消費端 → RGBA8；一個接受打包的消費端 → 切到打包（`generation`＋1、`layout`、矩形、貼圖尺寸與格式正確、`contentSerial` 持續遞增、切換那一個 tick 就有內容）；再加一個不接受的消費端或匿名消費端 → 切回 RGBA8；它離開（`release` 或 120 次更新淘汰）→ 再切回打包；30 tick 的遲滯；有 alpha 的素材用 `PACKED_YUVA420`；4:4:4 素材即使消費端接受也維持 RGBA8；同時輸出到材質時維持 RGBA8；`cev_allowPlanar 0` 維持 RGBA8。切換前後聲音不中斷（音訊時鐘連續：切換前後的 `timeSeconds` 差與牆鐘差一致，誤差 ≤ 50 ms；沒有重新載入的 log）。
- 引擎內像素驗證：打包排列時把貼圖讀回（引擎有現成的貼圖讀回 API 就用——例如 `ITexture::GetData32` 之類，先查證對 `eTF_R8` 是否可用；不可用則比對「送進 `UpdateTextureInVideoMemory` 的緩衝」與 Core 的打包緩衝，並以 `cev_probe_r8` 的做法截圖存證），確認上傳的內容與 Core 的打包緩衝相同。
- `cev_apitest`、`cev_flowtest`、`tools/smoke_test.sh`、Core／offline 自測全過（項目數變動寫進報告）。產生測試素材一律用明確路徑的 ffmpeg 7.1.1（`C:/Users/Bigspring/scoop/apps/ffmpeg-shared/current/bin`——PATH 上第一個 ffmpeg 是 ImageMagick 附帶的 4.2.3，會讓 `av_sync_flash_beep` 失敗）。
- 引擎內量測（GameLauncher，測試專案不載入 CryXTUI；`cev_stats_file`）：六支量測素材（`E:/coding3/xt-bench/cev-s0/media/`）各 20 秒，RGBA8 與打包兩種排列各一輪：解碼、複製、轉色、主執行緒上傳的 ms（平均／p99）、每幀上傳位元組、行程 RAM 增量、GPU 記憶體增量、掉幀。特別回報 2160p30 alpha 在打包排列下是否能即時播放。
