# M9 · 解碼後端可替換；Media Foundation 硬體解碼（讀回）；`Decode = Auto | GPU | CPU`

對應：`docs/design/M6-ui-source.md` §6、§10 的 Media Foundation 一段（階段 0 的實測——判定方式、VP8 無硬解、讀回要 `Flush`＋排隊 2 幀、貼圖高度對齊與 UV 起點、`STREAM_CHANGE`）、§5.1（ring 的打包排列）、§13。探測程式 `tools/probes/mf_decode_probe/`（階段 0 留下，可取用其做法；它不是產品碼）。前置：M6～M8 已併入（`SetDecode` 目前只記錄設定、`GetDecodeBackend` 恆為 CPU）。模型：Opus。工作樹 `E:/coding crycry/cev-wt-m9`，分支 `m9`。引擎樹 `E:/coding crycry/CRYENGINE_Source_CEVPlayer_XTFrame`。**不合併、不推送。**

使用者的決定（2026-11-19）：硬解用 Media Foundation；CPU 解是 fallback；GPU／CPU 可選，讓開發者依場合分配負載；素材只吃 WebM；**不加渲染器 patch**——硬解的輸出讀回記憶體後走與軟體解碼相同的路徑（零複製的第二版量測後再議，不在本單）。

動手前以程式核對前提；不符就停下回報。先寫會失敗的測試。Media Foundation／D3D11 的 API 細節以本機 Windows SDK 標頭與探測程式實際觀察到的行為為準，不憑印象。

## 要做的事

1. **後端介面**（Core）：視訊解碼抽成 `IVideoDecoderBackend`（建立／餵封包／取輸出寫入 ring slot 的打包排列／flush（seek）／關閉／回報後端種類與是否硬體）。libvpx 是其一（行為不變——既有 Core 自測逐項不變）。解封裝、時鐘、ring、skip 模式（seek 與 M7 的只解碼／補解）對兩種後端一致。
2. **Media Foundation 後端**（Core 內、只在 Windows 編譯；不依賴引擎）：
   - 以 `MFTEnumEx`（`MFT_CATEGORY_VIDEO_DECODER`，輸入 `MFVideoFormat_VP90`，同步＋非同步旗標）取得解碼 MFT；自己建立一個 D3D11 裝置（`D3D11_CREATE_DEVICE_VIDEO_SUPPORT`、多執行緒保護；adapter 選「預設顯示卡」——與引擎相同的那張；多顯示卡時以 DXGI 的第一個 adapter 為準並在 log 記錄名稱）與 `IMFDXGIDeviceManager`，`MFT_MESSAGE_SET_D3D_MANAGER`。
   - **判定硬體解碼＝給了 D3D manager 之後 `SetInputType` 成功且輸出樣本是 `IMFDXGIBuffer`**；否則這個播放器改用 libvpx（不使用「沒有 D3D manager 的 MF 軟體解碼」）。VP8 一律 libvpx。找不到 MFT（未安裝 VP9 Video Extensions）→ libvpx。
   - 輸出 NV12 貼圖 → 複製到 staging 貼圖 → `Flush` → 排隊 2 幀後 `Map` → 依 aperture 裁切、把 Y 與交錯的 UV 拆寫進 ring slot 的打包排列（Y 區、U 區、V 區）。處理：第一次輸出前的 `MF_E_TRANSFORM_STREAM_CHANGE`、貼圖高度對齊（1080 → 1088；UV 起點＝`RowPitch × 貼圖高`）、解析度與 stride。
   - alpha：第二條視訊流用第二個 MFT 實例；它開不了或不是硬體時，alpha 流單獨用 libvpx（色彩流仍用 MF）。alpha 的 Y 平面寫進打包排列的 A 區。
   - seek／loop／M7 的補解：flush MFT 後從關鍵幀重餵；skip 模式下不做讀回（只推進解碼器）。「只解碼」（剛看不見）在 MF 後端可以直接不餵封包嗎？——不行（之後要補解就需要參考幀）：照 libvpx 的語意餵封包但不讀回。
   - 執行緒：MF 的呼叫與 D3D11 context 都留在該播放器的解碼 worker 上；COM 初始化／反初始化在 worker 的生命週期內成對；不得在引擎的主執行緒或渲染執行緒上使用這個 D3D11 裝置。裝置遺失（`DXGI_ERROR_DEVICE_REMOVED`／`_RESET`）→ 該播放器改用 libvpx 從目前時間繼續（seek 到當下），記一次警告。
   - 失敗即退回：建立過程任何一步失敗都退回 libvpx，並保留失敗原因字串供 `cev_stats`／Ready 事件的 `DecodeBackend`／log 顯示。
3. **選擇**（模組）：`SetDecode(Auto|GPU|CPU)` 生效（Load 時決定；播放中改設定 → 記住，下次 Load／Play-from-stopped 生效，不中途重載）；全域 cvar `cev_decodeMode`（0 Auto、1 GPU、2 CPU；播放器沒有明確設定時使用）。`Auto`＝硬體可用且影片高度 ≥ `cev_decodeAutoMinHeight`（預設 1080）時用 GPU。`GPU` 而硬體不可用 → libvpx＋一次警告。`GetDecodeBackend()`、描述表的 `DecodeBackend` 查詢、Ready 事件、`cev_surfaces`、`cev_stats`（後端、硬體與否、讀回耗時 ms、MF 解碼呼叫耗時）回報實際結果。移除 M6b 的「hardware decode is not available in this build」警告。編輯器預覽（E2 的 `PreviewSession`）一律用 CPU 後端（不在本單引入預覽的硬解）。
4. **同時播放的上限**：硬體解碼器的實例數有限（依顯示卡）；第 N 個播放器建立 MF 後端失敗時照規則退回 libvpx——以同時開 6 個 1080p 播放器的測試確認不會失敗或卡住，並記錄實際有幾個拿到硬體。
5. **關閉順序**：播放器銷毀、插件關閉、行程結束時，MFT、樣本、staging 貼圖、D3D11 裝置在 worker 上釋放完畢才結束 worker；`MFStartup`／`MFShutdown` 以行程內計數成對。

## 測試

- Core 自測（獨立建置，不經引擎）：
  - 後端介面下 libvpx 的既有測試全過（6920 項不變或只增不減）。
  - MF 後端對六支量測素材（`E:/coding3/xt-bench/cev-s0/media/`）：解出的打包緩衝與 libvpx 後端**逐位元組相同**（Y、U、V、A 全部——階段 0 只比了 Y 與 A；若 UV 有差異，量化最大差與平均差並停下回報，不要放寬）；seek 到 20 個隨機時間點後第一張輸出與 libvpx 相同；loop 三圈；M7 的隱藏→停止→恢復在 MF 後端通過同一組測試。
  - VP8 素材：`GPU` 設定下實際後端為 libvpx。模擬「沒有 MFT」（測試用開關讓列舉回空）與「`SetInputType` 失敗」兩種退回。
  - 自測在沒有可用硬體解碼的機器上要能通過（MF 相關項目標示 skipped 並說明），不得因此失敗。
- 引擎內（GameLauncher，測試專案不載入 CryXTUI）：`cev_apitest`、`cev_flowtest`、`cev_contract_selftest` 全過（項目數變動寫進報告）；`Decode=GPU` 播 1080p30 與 2160p30 alpha 到 surface，`cev_stats` 顯示硬體後端；六個播放器同時；播放中 seek、暫停、隱藏／恢復；關閉時無崩潰、無殘留執行緒（log 與行程結束碼）。
- 量測（`cev_stats_file`，各 20 秒；RGBA8 與打包兩種排列 × CPU 與 GPU 兩種後端；素材：1080p30、1080p60、2160p30、2160p30 alpha）：解碼耗時（libvpx 的 ms；MF 的解碼呼叫＋讀回 ms）、複製、轉色、上傳、掉幀、**行程 CPU 使用率（整個行程的 CPU 時間／牆鐘）**與行程 RAM 增量（硬解時 libvpx 的參考幀緩衝應消失——§13 的拆解表裡 libvpx 佔 32～244 MB）、GPU 的 video decode 引擎使用率（能取得就記）。把結論寫成「哪些場合選 GPU、哪些選 CPU」的建議表（遊戲選單、開場、關卡內大螢幕、關卡內多個小螢幕），進報告，由主模型收進設計文件。

## 規則

- 第三方：只用 Windows SDK（Media Foundation、D3D11、DXGI）；不新增任何函式庫。連結的系統函式庫（`mfplat`、`mfuuid`、`d3d11`、`dxgi`…）加在 Core 的 CMake 與引擎端的 CMake 模組兩處並確認兩邊都建得起來。
- 引擎樹：只複製改過／新增／刪除的檔，不讓 SDK 目錄被刪掉重抄；檔案清單變動後 `Tools/Integration/Build.ps1 -ConfigureOnly`；只增量建 `CEVPlayer` 與 `EditorCEVPlayer`；不改引擎與 CryXTUI。CryVS 綁定在這棵樹編不到：保持原始碼一致並註明。Core 獨立建置的中間檔放 `T:/cev/m9/`（做完刪）；證據放 `E:/coding3/xt-bench/cev-m9/`。最多 8 個平行建置工作。
