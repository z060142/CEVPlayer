# 階段 0 · 只量不改：經由 UI 播放的五個前提與基準表

對應：`docs/design/M6-ui-source.md`（先讀 §2、§3、§5、§6、§7、§8）。模型：Opus。分兩張，可同時進行，各用自己的工作樹與分支；**不合併、不推送**，主模型收報告後合併。產出寫進各自的研究檔，主模型彙整成 `docs/research/05-ui-source-baseline.md`。

共同規則：
- 不改產品行為：可以加**只供量測**的東西（開發用主控台指令、`cev_stats` 的新欄位、獨立的探測程式），不得改動既有的播放路徑、節點、介面。
- 建置中間檔放 RAM 碟：`T:/cev/<用途>/`（Core 獨立建置、探測程式）；做完刪掉自己建的目錄。引擎樹的建置目錄（`win64/`，已存在）留在原地，只做增量建置。量測結果與要留的檔案放 `E:/coding3/xt-bench/cev-s0/`。
- 量測釘效能核（13600K：遮罩 `0xFFF`）：以 `subprocess.Popen` 啟動後立刻 `SetProcessAffinityMask`，或 PowerShell `(Start-Process … -PassThru).ProcessorAffinity = 0xFFF`；**不要用 `cmd /c start "" /affinity … > log`**（會卡住而程式從未啟動）。每個外部指令都給逾時；背景指令 10 分鐘沒輸出就檢查並改前景重跑。
- 最多 8 個平行建置工作。不動 `E:\coding2`、`E:\coding4`（唯讀）。不碰不是自己啟動的行程（啟動引擎前先確認沒有 `Sandbox.exe`／`GameLauncher.exe` 在跑；有就停下回報）。不 `git add -A`、不 `git stash`、不推送。
- 任務單的前提與程式不符時停下回報，不自行改設計。做不到的量測照實寫「未能量測」與原因，不以推論代替。
- 提交訊息英文、帶 `S0`、結尾 `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`。報告以繁體中文、精簡：每個問題的答案與證據（檔案、指令、數字）、沒做到的、對設計文件的修正建議。

## S0-A · 獨立部分（工作樹 `E:/coding crycry/cev-wt-s0a`，分支 `stage0/standalone`）

1. **Core 獨立建置與自測**：照 `Code/CryPlugins/CEVPlayer/Core/CMakeLists.txt` 在 `T:/cev/core/` 建 Release，產生測試素材（`tools/make_test_media.sh`；系統有 scoop 的 ffmpeg），跑 `cevcore_selftest`，記錄結果。素材另產生量測用的 1080p30、1080p60、2160p30（VP9，各一支無 alpha、一支有 alpha；關鍵幀間隔 2 秒），放 `E:/coding3/xt-bench/cev-s0/media/`。
2. **Core 的基準數字**（不經引擎）：寫一個小的量測程式（`tools/probes/core_bench/`，連 Core）或用自測既有的計時，對上述素材量每幀的解碼、平面複製、YUV→RGBA 轉換的 ms（平均、p99）、ring 佔用的 RAM、每幀位元組數；`decodeThreads` 自動值與 1。
3. **色度位置**：讀 `Core/src/ColorConvert.cpp` 與解封裝處，回答 (a) 現行 CPU 轉換對 4:2:0 的色度取樣是最近點還是內插、等效於哪一種位置（left／center／top-left）；(b) 素材的 Matroska `ChromaSitingHorz/Vert` 有沒有被讀、測試素材與 FFmpeg 轉出的素材標的是什麼；(c) 契約的 `chromaSiting` 應回報什麼、`flags` bit3（色彩平面是否已乘 alpha）對 VP9 alpha 素材應為何。
4. **Media Foundation 硬體解碼探測**：寫獨立程式 `tools/probes/mf_decode_probe/`（連 Core 的 libwebm 解封裝或直接讀 IVF／webm；不進產品目標）：以 `MFTEnumEx` 取得 `MFVideoFormat_VP90`／`VP80` 的解碼 MFT，分別在「沒有 D3D manager」與「給它一個自己建立的 D3D11 裝置（與預設顯示卡相同、`D3D11_CREATE_DEVICE_VIDEO_SUPPORT`、多執行緒保護）」下解上述素材。回報：MFT 名稱與來源、是否回報 D3D11-aware、輸出樣本是否為 `IMFDXGIBuffer`（NV12 貼圖）、輸出格式／尺寸／stride、每幀解碼耗時與行程 CPU 使用、VP8 是否可用、alpha 第二條流是否能以第二個 MFT 解、把輸出複製到 staging 貼圖並 Map 讀回的每幀耗時（同步與延後 1～2 幀的非同步各量）、seek（flush 後從關鍵幀重餵）是否正常、解出的畫面與 libvpx 的差（逐像素比對 Y 平面的最大差與平均差）。本機顯示卡：以程式列出 adapter 名稱。
5. 寫 `docs/research/05a-standalone.md`。

## S0-B · 引擎內（工作樹 `E:/coding crycry/cev-wt-s0b`，分支 `stage0/engine`；引擎樹 `E:/coding crycry/CRYENGINE_Source_CEVPlayer_XTFrame`，已建置 Profile）

先讀引擎樹的 `INTEGRATION.md`、`Tools/Integration/Build.ps1`、本倉 `tools/sync_sources.sh`、`tools/smoke_test.sh`、`docs/research/03-smoke-test.md`。引擎樹裡的 CEVPlayer 原始碼是複本：以 `tools/sync_sources.sh` 從你的工作樹同步進去，只增量建置 `CEVPlayer` 目標（必要時 `CryRenderD3D11` 不得重建——本單不改渲染器）。引擎樹其他檔案不改。

1. **`eTF_R8` 動態貼圖**：先唯讀確認格式表（`DeviceFormats`、`TextureDataSize`、`GetOrCreate2DTexture`、`RT_UpdateTextureRegion` 的格式檢查）；再加一個開發用指令 `cev_probe_r8 <w> <h>`：以 `UploadToVideoMemory(nullptr, w, h, eTF_R8, …, FT_NOMIPS)` 建立、每幀以 `UpdateTextureInVideoMemory(…, eTF_R8)` 更新一個會變的圖樣、用 aux 把它畫在畫面一角（R8 在 aux 著色下會顯示成紅色通道或灰階——照實描述）、截圖存證。非 2 的冪與 `w × (h + h/2)` 這種尺寸（1920×1620、3840×3240）各試。回答：是否成功、有沒有 assert／警告、實際的裝置格式。
2. **同一幀還是晚一幀**：設計並執行一個量測，判定「CEVPlayer 在 `UpdateBeforeRender` 送出的貼圖更新」與「CryXTUI（XUI2D）在同一個主幀送出的 UI 繪製」是否在同一個顯示幀生效。建議做法：開發用指令讓 CEVPlayer 每個主幀把貼圖填成編碼了幀序號的純色；用既有的 `xtui_bind_texture` 把該貼圖綁進一個顯示 `engine://` 圖的測試 UI（引擎樹的 CryXTUI 是 v0.17.0，照它的 selftest／範例 bundle 找一個可用的，或用 `Draw2dImage` 以外的現成 XTUI 測試面）；同一幀另以 aux 在旁邊畫出同一個序號的色塊；截圖比較兩塊顏色是否相同。做不到（例如沒有可用的測試 bundle）就照實回報卡在哪一步與替代證據（讀 render command 排隊順序的結論要標「推論」）。
3. **引擎內基準**：`cev_stats` 補量測欄位——主執行緒上傳呼叫耗時（平均、p99）、每幀上傳位元組、複製與轉色分開（若 Core 尚未分開計時，在 Core 加兩個計數器即可）；`cev_stats_file <path>` 寫 CSV（每秒一列）。以 S0-A 的六支素材（或自行以同一腳本產生）在 GameLauncher 內播放各 20 秒，輸出到具名貼圖（不開全螢幕），記錄解碼、複製、轉色、上傳的 ms 與位元組、行程 RAM 的增量、GPU 記憶體（能取得就記，取不到寫未量）。
4. 檢查現有的引擎內自測仍過（`cev_apitest`、`tools/smoke_test.sh` 能跑的部分）。
5. 寫 `docs/research/05b-engine.md`。
