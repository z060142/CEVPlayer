# M10 · 關卡讀取期間播放（M10a 已完成 2026-11-20；M10b 定案待派）

依據：使用者 2026-11-19「XTFrame 必須能在關卡讀取時跑…CEVPlayer 等它完成以後參考它的方案」。設計前提：`docs/design/M6-ui-source.md` §9、§9.1。引擎介面（主線 CE-90，CE 倉 `patches/17-loadtime-callbacks.patch`、`patches/README.md` 第 17 條）：`IRenderer::AddLoadtimeCallback(ILoadtimeCallback*, int order)`／`RemoveLoadtimeCallback(ILoadtimeCallback*)`，只限主執行緒；每圈先依 order 遞增呼叫每個回呼的 `LoadtimeUpdate(dt)`（鎖外），再呼叫每個 `LoadtimeRender()`（鎖內），最後 present 一次；慣例來源 100、UI 200。

模型：Opus。分兩張：**M10a 探測**（不改播放行為，只加探測與量測）→ 主模型依結果定案 → **M10b 實作**。兩張都不合併、不推送。

## 已定的方案（M10a 不得更動，M10b 照做）

1. **未修補的引擎照常能編、行為不變**：回呼相關程式只在 CMake 於引擎的 `IRenderer.h` 找到 `AddLoadtimeCallback` 時編入（定義 `CEV_HAVE_LOADTIME_CALLBACKS=1`）。沒有時維持現況：讀取期間時鐘暫停、不呼叫渲染器（`CPlayerManager::BeginLevelLoading`）。
2. **執行期再確認一次**：只有渲染器模組匯出 `XUI2D_Patched` 且第 7 位元（128）為 1 才使用新介面（`GetProcAddress`，不引用任何 XTFrame 標頭；匯出函式的簽名以主線回覆為準，M10a 核對）。否則同第 1 點的現況。
3. **依意圖註冊**（2026-11-20 依主線意見修訂）：回呼（order 100）在「有活著的播放器，或有尚未處理的 open／play 指令」時就註冊，兩者皆無時移除。單純載入插件的專案不會因為我方而啟動讀取迴圈。理由：讀取畫面的 UI 在 `LEVEL_LOAD_START_LOADINGSCREEN` 於主執行緒預熱時才送 `open`，此時播放器還沒 tick 過；只看「正在播放」會讓讀取畫面影片永遠起不來。
4. **讀取模式下誰會動**：Surface 輸出一定要動；全螢幕輸出視 M10a 的探測（讀取迴圈內 `IRenderAuxImage::Draw2dImage` 是否出畫面）；材質輸出維持暫停（材質在卸載／載入中）。關卡卸載時腳本擁有的播放器照舊被銷毀（`DestroyScriptOwned`）。
5. **時間**：讀取模式用 `LoadtimeUpdate(dt)` 給的 dt 推進（單次上限 0.25 秒，超過視為停頓、不追幀）；不讀 `gEnv->pTimer`、不用任何幀編號。現況盤點（2026-11-20）：模組內沒有使用渲染／主幀編號；`GetAsyncCurTime` 的使用點在 `PlayerManager.cpp:35`、`Plugin.cpp:124` 與測試／開發指令。
6. **執行緒**：tick 本體加一把不競爭的鎖，主執行緒入口與讀取回呼入口不會同時跑；讀取模式中不碰 entity／flow／Schematyc、不發事件到腳本（事件排隊，讀取結束後在主執行緒發出）。
7. **讀取期間的指令由讀取模式的 tick 處理**（修訂）：契約的 `open`／`control` 與描述表指令照舊只排隊（§3 規則 10 不變），但讀取模式下由 `LoadtimeUpdate` 這個 tick 取出套用，不等主執行緒的 tick。主線的消費端只在預熱（迴圈開始前、主執行緒）送 `open`，第一版不在迴圈內呼叫 open／close；`query`／`hint` 每圈由回呼執行緒（order 200）呼叫。
   - 若 P5／P8 證明在 `LockReadIO` 下由渲染執行緒開檔安全：`open` 一律在讀取模式的 tick 內開檔。
   - 若不安全：退路是「讀取已開始（`m_levelLoading`）且呼叫者是主執行緒時，在 `open` 呼叫當下同步開檔」（規則 10 的明文例外，需同步改兩邊的契約文件），並以 `state` loading → ready 呈現。不得依賴系統事件監聽者之間的順序。迴圈內才送達的 open 排到讀取結束。
8. **貼圖被釋放**：若 M10a 證實卸載段會釋放我方貼圖，重建後 `generation` 加一（契約既有語意）。

## M10b 實作（2026-11-20 定案；依據 `docs/design/M6-ui-source.md` §9.2）

工作樹 `E:/coding crycry/cev-wt-m10`、分支 `m10`（接續 M10a 的 2aa6abb；先 `git merge rebuild` 取得之後的文件提交）。動手前以程式核對下列現況，不符就停下回報。先寫會失敗的測試。M10a 的探測指令保留。

### 現況（`Module/Player/PlayerManager.*`）

`UpdateBeforeRender(dt)` 在 `m_levelLoading` 時直接返回；`BeginLevelLoading` 對每個播放器呼叫 `OnLevelLoadBegin()`（暫停時鐘）；`RenderCallsAllowed()` 在讀取期間為 false；事件只在 `UpdateBeforeRender` 內由 `DispatchEvents()` 發出；契約指令只在 `ProcessContractCommands()` 套用。

### 要做的

1. **cvar `cev_loadtime`**（int，預設 1；`PluginEnv`）：0＝舊行為。說明字串：`Keep texture-only players running during level loading screens (needs a renderer with load-time callbacks). 0 = pause everything while a level loads`。
2. **可用性**（`Module/Render/RenderBridge.*`）：`bool RenderBridge::LoadtimeAvailable()`——未定義 `CEV_HAVE_LOADTIME_CALLBACKS` 時固定 false；否則第一次呼叫時以 `GetModuleHandle`＋`GetProcAddress` 讀渲染器模組的 `XUI2D_Patched`（`extern "C" int XUI2D_Patched()`）並快取 `(值 & 128) != 0`。把 M10a 探測碼裡相同的讀取改成呼叫它。
3. **鎖**：`CPlayerManager` 加 `std::recursive_mutex m_tickMutex`。下列入口整段持有：`UpdateBeforeRender`、`UpdateAfterRender`、`CheckLevelLoadingTimeout`、`OnSystemEvent`、`CreatePlayer`、`CreatePlayerForSurface`、`DestroyPlayer`、`Shutdown`、新的 `LoadtimeTick`，以及描述表的呼叫分派入口（`Module/Bindings/ApiTable.cpp` 有 `IsMainThread()` 檢查的那個分派函式；經由管理員提供的 `std::recursive_mutex& TickMutex()`）。契約函式照舊不取鎖（它們只碰自己的佇列與快照）。
4. **回呼**（`PlayerManager.cpp`，僅 `CEV_HAVE_LOADTIME_CALLBACKS`）：內部類別 `CLoadtimeCallback final : public ILoadtimeCallback`，`LoadtimeUpdate(float dt)` 呼叫 `m_manager.LoadtimeTick(dt)`，`LoadtimeRender()` 空實作。
5. **`void CPlayerManager::LoadtimeTick(float dt)`**（渲染執行緒）：取鎖；`m_shutdown` 或 `cev_loadtime==0` 則返回；`dt = clamp(dt, 0, 0.25f)`；`m_clock += dt`；設 `m_inLoadTick=true`（返回前清除）；`ProcessContractCommands()`；對每個 `p->RunsDuringLoad()` 的播放器 `p->Tick(dt)`。**不**呼叫 `DispatchEvents`、`LogStats`、`ReapZombies`、`ReapPendingDestroy`、`CheckDecoderShutdown`，不讀 `gEnv->pTimer`。事件留在播放器的佇列裡，讀取結束後第一次 `UpdateBeforeRender` 照常發出。
6. **`bool CVideoPlayerImpl::RunsDuringLoad() const`**：只輸出到貼圖（不是全螢幕、沒有綁材質）。`CreatePlayer`／`CreatePlayerForSurface` 建出、沒有 `SetFullscreen(true)`、沒有材質綁定者為 true。
7. **`RenderCallsAllowed()`**：`!m_shutdown && RenderBridge::Available() && (!m_levelLoading || m_inLoadTick)`。讀取期間主執行緒上的呼叫（例如銷毀）照舊延後（zombie）。
8. **讀取開始／結束**：`OnLevelLoadBegin()` 改為 `OnLevelLoadBegin(bool keepRunning)`；`BeginLevelLoading` 對每個播放器傳入 `LoadModeActive() && p->RunsDuringLoad()`，為 true 的播放器不暫停時鐘。`bool LoadModeActive() const`＝`cev_loadtime != 0 && m_loadtimeRegistered`。讀取期間才建立的播放器（契約 `open`）同樣依此決定是否一開始就處於暫停。`EndLevelLoading` 行為不變（對沒被暫停的播放器 `OnLevelLoadEnd()` 必須是 no-op——核對並在測試中驗證沒有時鐘跳動）。
9. **註冊**：`void CPlayerManager::UpdateLoadtimeRegistration()`（主執行緒；非主執行緒呼叫直接返回）。`want = !m_shutdown && cev_loadtime != 0 && RenderBridge::LoadtimeAvailable() && (!m_players.empty() || 契約佇列非空)`；`want != m_loadtimeRegistered` 時呼叫 `gEnv->pRenderer->AddLoadtimeCallback(cb, 100)`／`RemoveLoadtimeCallback(cb)`。契約佇列是否非空由 `Module/Contract/TexSource.*` 加一個唯讀查詢（名稱 `HasPendingCommands()`，只讀自己的佇列，不呼叫引擎）。呼叫點：`UpdateBeforeRender` 開頭、`CreatePlayer*` 與 `DestroyPlayer` 結尾、`OnSystemEvent` 的 `ESYSTEM_EVENT_LEVEL_LOAD_START_LOADINGSCREEN`（在 `BeginLevelLoading` **之前**）與 `ESYSTEM_EVENT_LEVEL_LOAD_START`。`Shutdown()` 內一定移除。
10. **暫停中 seek 的序號**（`VideoPlayerImpl.cpp` 的 `Seek()`，M10a P9：約 :794 設 `m_needUpload=true`）：seek 後在目標幀解出之前不上傳、不遞增 `contentSerial`；一次暫停中的 seek 恰好遞增 1。若拿掉該旗標會讓某條既有自測失敗，停下回報那條自測與原因，不自行另尋解法。
11. **解碼池的收尾**：核對 `CPlayerManager::Shutdown()` 返回時 `DecodePool` 的執行緒是否已全部 join（`AcquireShared` 是否留有靜態的強參考）。已 join：在報告註明依據。沒有：只回報，不修。
12. **`cev_info`／`cev_surfaces`** 加一行讀取模式狀態：`loadtime: available=<0|1> registered=<0|1> cev_loadtime=<n>`。
13. **文件**：README 的 cvar 表加 `cev_loadtime`；Features 與 Limitations 裡「讀取畫面期間不前進」的句子改寫為實際行為（只輸出到貼圖的播放器在有讀取期回呼的渲染器上持續播放；全螢幕與材質輸出暫停；未修補的引擎全部暫停）；CHANGELOG 加一條。
